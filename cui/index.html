Design System

Designing a White-Label Design System for 120+ Credit Unions

Role Lead Designer
Company Clutch
Timeline 2024
Team Designers, Front-End Engineers, PMs, QA
TL;DR
What

A unified design system replacing fragile MUI components with themeable React components and design tokens across Staff and Online Portals for 120+ credit unions.

Problem

Two separate frontends, broken MUI components, duplicate engineering effort, and no shared design language across products. Every new feature added more inconsistency.

Approach

UI audit, token architecture, 40+ components in Figma and React, stakeholder buy-in through working prototypes, and documented onboarding for adoption.

Challenges

Cross-team alignment, legacy MUI deprecation, white-labeling for 120+ brands while maintaining WCAG AA accessibility.

Result

Faster feature delivery, fewer visual QA bugs, and a single source of truth adopted across all new product work. Engineering began replacing MUI component by component.

Overview

Multiple fintech products, zero shared design infrastructure

The company was shipping fintech tools across two portals without shared components, tokens, or design principles. Legacy MUI was tightly coupled, theming was rigid, and white-labeling for 120+ credit unions was unsustainable.

I owned the full design system effort -- from strategic framing to component delivery:

  • UI audit and component inventory across both portals
  • Token architecture -- primitive, semantic, and component-level
  • Figma library -- production-ready, maintained, and documented
  • React + Storybook -- coded core components, managed documentation
  • MUI deprecation strategy -- partnered with engineering on phased rollout
  • Adoption and advocacy -- cross-team workshops, onboarding, governance

Stakeholders: product leadership, engineering managers, marketing, exec team. I collaborated across multiple squads with designers, front-end engineers, PMs, and QA.

The Problem

Scaling fast, but every feature shipped more inconsistency

  • Broken MUI components across all products -- no one owned them
  • Two separate frontends for branch officers and loan applicants, built independently
  • 120+ credit unions each needing brand-matched UI
  • Duplicate work -- teams rebuilding the same components with minor variations
  • Inconsistent UX -- same interaction patterns behaving differently per product

Spot the inconsistencies. Each element had separate code. No shared components existed between products.

120+ credit unions requiring unique branding

Strategy

Framing the system around jobs, not components

I anchored the system's direction in four strategic questions:

  • How might we reduce handoff friction with shared building blocks?
  • How might we support white-labeling without fragmenting the experience?
  • How might we build consistency without killing flexibility?
  • How might we scale for future products and teams?

Then grounded the approach in Jobs to Be Done:

Designer: Assemble UI quickly with confidence it scales. Engineer: Build features without rethinking every visual decision. Product: Launch fast while preserving quality and accessibility.

Stakeholder Buy-In

MUI was "working" -- convincing the org to invest in infrastructure

Buy-in wasn't immediate. Teams were shipping features and MUI was "good enough." My approach: use the new Staff Portal as a proof of concept -- build it right from day one, no MUI, clean components in Storybook.

  • Prototyped the pain: rebuilt our worst components to show the new system's clarity and maintainability
  • Side-by-side comparisons: broken MUI vs. unified system -- made the gap undeniable
  • Estimated dev-time savings: worked with engineers to quantify the ROI of shared components

The card component became the proof point -- scalable, reusable, and immediately valuable across multiple contexts.

The same card component in production after rollout.

The Staff Portal proved the system worked. Engineering began deprecating MUI in the Online Portal, replacing it component by component.

White-Labeling

One system, 120+ brand identities

Every product needed to match the partner credit union's brand. I designed a flexible token architecture with a Figma theming system to toggle between brand presets -- validating themes visually without duplicating files.

Each credit union's primary brand color, applied to interactive elements only.

Live theme switching in Figma. Interactive elements use brand colors; system colors (like status badges) stay fixed. Same capability existed in Storybook.

White-labeled mobile experience with brand palette and customizable copy.

The trade-off: controlled customization

Credit unions wanted full brand control. That wasn't scalable or accessible. I aligned with Customer Success on a constraint: one primary brand color per CU -- everything else follows system rules. For inaccessible brand colors, I built fallback system colors to preserve contrast.

Trade-off: One primary color, not unlimited overrides. Why: Prevents fragmentation, maintains accessibility, keeps theming logic predictable. Result: CUs felt represented. The system stayed cohesive.

Two Portals, One System

Same building blocks, different contexts

  • Staff Portal: Desktop-only, information-dense, task-focused. Used by CU employees in-branch
  • Online Portal: Mobile-first, embedded in CU apps. Used by members applying for loans. Trust and simplicity are critical

Left: Staff Portal -- dense, task-oriented. Right: Online Portal -- clean, mobile-first, embedded.

The goal was flexibility without fragmentation:

  • Responsive variants for navigation, tables, and forms
  • Adaptive theming -- broader color use on Staff, stricter brand adherence on Online
  • Context-aware documentation per audience and portal
  • Shared core, different wrappers -- base components reused in portal-specific layouts

Measuring Success

Tracking impact across design, engineering, and delivery

  • Feature delivery time: design-to-dev handoff and release cycle durations before and after adoption
  • Visual QA issues: UI inconsistency bugs tracked through QA tickets and customer feedback
  • Adoption metrics: Figma usage analytics, Storybook contributions, production component usage
  • Theming efficiency: time to implement new Credit Union themes using the token system
  • Team feedback: surveys and 1:1s on design-dev collaboration friction
  • Accessibility: WCAG AA compliance through automated and manual audits
Reflection

What I learned, what I'd change

Key takeaways

  • Buy-in requires proof, not pitches. Working prototypes and dev-time estimates moved stakeholders faster than slide decks
  • Design with engineering constraints. Token architecture decisions shaped what engineers could build efficiently
  • Systems are products. Governance, contribution paths, and onboarding matter as much as the components themselves

What I'd do differently

  • Involve stakeholders earlier -- co-create the vision from day one to accelerate ownership
  • Define contribution paths upfront -- reduce confusion around proposing and updating components
  • Automate accessibility checks sooner -- catch WCAG issues across white-label variations before they compound
  • Test with end users earlier -- especially for the mobile-heavy Online Portal

This project reinforced a core belief: design systems succeed when they unify people, not just pixels. Strategy, cross-functional alignment, and adoption matter as much as the component library itself.
